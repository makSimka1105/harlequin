# Панель связей и сборка JOIN

Дата: 2026-09-24
База: ветка `maksibon-fork`
Заменяет раздел 2 спеки `2026-09-20-harlequin-fork-design.md` (панель связей).

## Задача

Две вещи, у которых общее ядро:

1. **Панель связей** отражает курсор каталога и позволяет ходить по FK-графу,
   вставлять путь до таблицы, до поля или готовый JOIN.
2. **JOIN-пикер** — модалка из редактора: читает `from`/`join` statement под
   курсором и предлагает, что к нему можно присоединить.

Попутно логика вставки уходит из `app.py` в отдельные модули. Остальная чистка
форка (`vimnav`, `tree.py`, `filtered_tree.py`, комментарии в `pgfk`) — отдельная
спека после этой.

## Решения

| Вопрос | Решение |
|---|---|
| Что отражает панель | Курсор каталога; таблица и любое её поле дают один и тот же вид |
| Курсор на поле | Связи через это поле поднимаются наверх и подсвечиваются, остальные не скрываются |
| Поля связанной таблицы | Не показываются, для этого есть каталог |
| Строка связи | Одна строка: направление, таблица, `N:1`/`1:N`, `?` для nullable, ближняя колонка |
| Детали связи | Футер с точным `on` для строки под курсором |
| Маршруты (бывший FURTHER) | Строки `⋯ цель  N шага` в конце того же списка, переключаются `f` |
| Навигация | Цепочка: `l` шаг по связи, `h` назад, крошки пути сверху |
| Вставка | `⏎` — таблица; `Tab` в футер, там `⏎` — одно из двух полей; `J` — join |
| Нет источника в запросе | Нет `from` — вставить `from источник` и join; `from` есть — уведомление, ничего не вставлять |
| Виды связи в v1 | `N:1`/`1:N` и nullable → `left join`. 1:1 и M:N не различаются |
| Пикер | Плоский список с фильтром, превью SQL внизу |
| Алиасы | Первая буква имени (слова через `_` дают аббревиатуру), при коллизии цифра: `p`, `p2` |
| Бинд пикера | `ctrl+l` в редакторе |
| Комментарии в коде | Без абзацев, максимум одна строка там, где причина неочевидна |

## Раскладка модулей

```
harlequin/relations/            чистое ядро, без textual
  graph.py      RelationGraph, Link, Route
  scope.py      разбор statement: таблицы, алиасы, точка вставки
  spelling.py   path_for и кавычки (переезд из references.py)
  joins.py      plan_joins: маршрут + scope → текст и место вставки
  candidates.py что можно присоединить к запросу
harlequin/relations_service.py  граф + поиск по каталогу + зарезервированные слова
harlequin/catalog_lookup.py     поиск CatalogItem по identifier (переезд из app.py)
components/relations_panel.py   панель, переписывается
components/join_picker.py       ModalScreen
harlequin_pgfk                  nullable в ForeignKeyEdge
```

`harlequin/relations.py` и `harlequin/references.py` исчезают, их содержимое
расходится по пакету `relations/`.

## Ядро

### graph.py

`ForeignKeyEdge` получает `nullable: bool = False`: истина, если хоть одна
колонка ключа на ссылающейся стороне допускает null. `pgfk` берёт это из
`attnotnull`. Адаптеры, не знающие nullable, оставляют `False`.

`Link` — ребро, увиденное с одного конца:

- `direction`: `out` (ближняя таблица ссылается) или `in` (на неё ссылаются);
- `near_relation`, `far_relation`, `near_columns`, `far_columns`;
- `cardinality`: `N:1` для `out`, `1:N` для `in`;
- `nullable`: только для `out`; для `in` всегда `False`.

`Route` — кортеж `Link`, `target` = `far_relation` последнего шага. Обход BFS в обе
стороны, до 4 шагов, каждая цель один раз по кратчайшему маршруту, при равенстве
алфавитно первым. Это поведение сохраняется из текущего `relations.py`.

`RelationGraph`:

- `links_for(relation) -> list[Link]`;
- `routes_from(relation, max_steps) -> list[Route]` — только маршруты от 2 шагов;
- `covers(database) -> bool`.

### scope.py

`read_scope(statement: str) -> BufferScope` (имя класса сохраняется):

- `relations: tuple[RelationRef, ...]` — `name`, `alias`, `is_cte`, как сейчас, плюс
  `top_level`: подстановка алиасов при вставке пути смотрит на все relations,
  JOIN — только на верхний уровень;
- `anchor: int | None` — смещение в тексте statement, после которого встаёт
  следующий join: конец последнего узла `join`, иначе конец последнего `relation`
  внутри `from`; `None`, если `from` нет;
- `indent: str` — отступ строки, на которой стоит `anchor`.

Верхний уровень — узлы, у которых нет
предка-подзапроса и которые не лежат внутри тела CTE. Проверено на парсере:
`join` и `relation` дают точные координаты; узел `from` тянется до конца
`order by`, поэтому для anchor не используется.

`BufferScope.alias_for` и сопоставление по суффиксу сегментов переезжают сюда без
изменения поведения.

### spelling.py

`path_for(item, owner, scope, reserved, known_relations)` и правила кавычек
переезжают из `references.py` без изменений. Добавляется
`spell_relation(identifier, reserved) -> str` для имени таблицы в join.

### joins.py

```python
plan_joins(route, scope, reserved) -> JoinPlan | JoinRefusal
```

1. Источник — `near_relation` первого шага. Ищется в `scope` через `alias_for`.
   - найден — его алиас (или имя, если алиаса нет) становится известной стороной;
   - не найден, `anchor is None` — план начинается с `from <источник> <алиас>`;
   - не найден, `from` есть — `JoinRefusal("<источник> нет в запросе")`.
2. Для каждого шага: если `far_relation` уже есть в scope, join не пишется, его
   алиас становится известной стороной для следующего шага. Иначе строка:
   `<тип> <таблица> <алиас> on <алиас>.<far_col> = <известный>.<near_col>`.
3. Тип — `left join`, если шаг `out` и `nullable`, иначе `join`.
4. Составной ключ — равенства через ` and `, в порядке колонок ключа.
5. Алиас — первая буква имени таблицы; если в имени есть `_`, первые буквы
   слов. Занятый алиас (из scope или уже выданный в этом плане) получает цифру
   начиная с 2. Сравнение без учёта регистра.
6. Имена таблиц — через `spell_relation`.

`JoinPlan(anchor: int | None, text: str)`. Если в statement уже есть `from`,
`anchor` = `scope.anchor`, `text` начинается с `\n` + `indent`, строки цепочки
разделены `\n` + `indent`. Если план начинается с `from`, `anchor is None` и
текст вставляется в позицию курсора.

`JoinRefusal(reason: str)` — текст для уведомления.

### candidates.py

`join_candidates(scope, graph) -> list[Route]`: для каждой таблицы scope (кроме
CTE) — её `Link` как маршруты из одного шага, плюс `routes_from` от 2 шагов. Цели,
которые уже есть в scope, отбрасываются. Прямые связи остаются все, по одной на
ключ (два FK в одну таблицу — два кандидата). Маршрут — один на цель, кратчайший,
при равенстве — от таблицы, раньше встречающейся в запросе; цель, до которой есть
прямая связь, маршрутом не дублируется.
Порядок: сначала прямые, потом по длине, внутри — по имени цели.

## RelationsService и CatalogLookup

`CatalogLookup` — то, что сейчас `_find_catalog_item`, `_children_of` и
`_known_relations` в `app.py`: поиск `CatalogItem` и владельца по identifier с
ленивой подгрузкой детей и список известных relations. Вызывается из воркера.

`RelationsService` держит `RelationGraph`, `CatalogLookup` и зарезервированные
слова:

- `path_text(identifier, database, statement) -> str | None`;
- `join_edit(route, statement, statement_offset) -> Edit | JoinRefusal`, где
  `Edit(offset, text)` — абсолютная позиция в буфере.

В `app.py` остаются короткие обработчики: получить statement под курсором,
вызвать сервис, применить правку или показать уведомление. `_insert_text_for`,
`resolve_and_insert_path` и методы поиска по каталогу из `app.py` удаляются.

## Панель связей

`RelationsPanel(Vertical)`: строка крошек, `OptionList` связей, футер.

```
┌ Relations ──────────────────────────┐
│ customer                            │
│─────────────────────────────────────│
│▌→ person            N:1? personid   │
│ ← salesorderheader  1:N  customerid │
│ ⋯ posterminal       2 шага          │
│ ⋯ salesorderdetail  2 шага          │
│─────────────────────────────────────│
│ on customer.personid =              │
│    person.personid                  │
│ nullable → left join                │
└─────────────────────────────────────┘
```

Состояние: `root: str | None` (таблица из каталога), `path: tuple[Link, ...]`,
`highlight_column: str | None`, `show_routes: bool`.

- `show(item, database)` — вызывается по `NodeHighlighted` дерева каталога.
  Колонка даёт `root` = её таблица и `highlight_column`; таблица —
  `highlight_column = None`. Путь сбрасывается.
- Текущая таблица = `far_relation` последнего шага `path`, иначе `root`.
- Строки: `links_for(текущая)`; при `highlight_column` связи через неё идут
  первыми и подсвечены. Затем, если `show_routes`, `⋯`-строки маршрутов.
- Футер показывает `on` и подсказку nullable для строки под курсором; для
  `⋯`-строки — цепочку таблиц маршрута.
- Схема, база, адаптер без FK — приглушённая строка, высота панели не меняется.

Бинды внутри панели:

| Клавиша | Действие |
|---|---|
| `j` / `k` | по строкам |
| `l` | шаг: `Link` добавляется в `path`, для `⋯` — весь маршрут |
| `h` | шаг назад по `path` |
| `⏎` | `InsertPath(far_relation)` |
| `Tab` | фокус в футер; в футере две строки-поля, `⏎` — `InsertPath(колонка)` |
| `J` | `InsertJoin(route)`: маршрут от `root` по `path` плюс строка под курсором |
| `f` | показать/скрыть маршруты |

Сообщения наружу: `InsertPath(identifier, database)`, `InsertJoin(route, database)`.

## JOIN-пикер

`JoinPicker(ModalScreen[Route | None])`, открывается `ctrl+l` из редактора.

```
┌ Join ───────────────────────────────────────┐
│ > _                                         │
│─────────────────────────────────────────────│
│▌→ person            N:1?  c.personid        │
│ → posterminal       N:1   soh.posterminalid │
│ ← salesorderdetail  1:N   soh.salesorderid  │
│ ⋯ product           2 шага via sod          │
│─────────────────────────────────────────────│
│ left join person.person p                   │
│   on p.personid = c.personid                │
└─────────────────────────────────────────────┘
```

- Кандидаты — `join_candidates` по statement под курсором, считаются один раз при
  открытии.
- `Input` сверху, фильтр — подстрока по имени цели без учёта регистра.
- Превью — `plan_joins` для выделенного кандидата.
- `⏎` — `dismiss(route)`, `Esc` — `dismiss(None)`.
- Кандидатов нет — приглушённая строка «нечего присоединять».

Действие `code_editor.show_join_picker` регистрируется в `actions.py`, бинд
`ctrl+l` добавляется в раскладку `vimnav`.

## Ошибки

| Ситуация | Поведение |
|---|---|
| Адаптер без `get_foreign_keys` или FK нет | Панель и пикер показывают «нет внешних ключей» |
| Курсор вне statement или буфер пуст | План начинается с `from` и вставляется в позицию курсора |
| Источник не в запросе, `from` есть | Уведомление из `JoinRefusal` |
| Элемент не найден в каталоге | Warning-уведомление, как сейчас |
| Буфер с синтаксической ошибкой | scope строится из того, что распарсилось; `anchor` может оказаться `None` |

## Тесты

Юниты ядра, без UI:

- `scope`: anchor после последнего join; после from без join; без from; relation
  из подзапроса не учитывается; тело CTE не учитывается; незаконченный join
  посреди набора.
- `joins`: один шаг; цепочка, где средняя таблица уже в запросе; nullable →
  `left join`; входящая связь → `join`; составной ключ; self-reference получает
  новый алиас; коллизия алиасов `p`, `p2`; нет источника без from → план с from;
  нет источника с from → отказ.
- `candidates`: цель из двух таблиц запроса показывается один раз; уже
  присоединённая таблица отброшена; порядок.
- `graph`: nullable учитывается только для `out`; маршруты как в старых тестах.

Функциональные (pilot):

- панель: курсор каталога на поле поднимает его связь наверх; `l`/`h` меняют
  крошки; `⏎` вставляет таблицу с алиасом из запроса; `Tab`+`⏎` вставляет поле;
  `J` добавляет join под последним join.
- пикер: фильтр сужает список; `⏎` вставляет join; `Esc` ничего не меняет.

Снапшоты: панель на таблице, панель на поле, пикер. Старые тесты панели
переписываются под новый вид.

## Порядок реализации

1. Пакет `relations/`: перенос `relations.py` и `references.py` без изменения
   поведения, старые тесты зелёные.
2. `scope.anchor`, `joins.py`, `candidates.py` с юнитами.
3. `nullable` в `ForeignKeyEdge` и запросе `pgfk`.
4. `CatalogLookup` и `RelationsService`, вынос кода из `app.py`; поведение
   прежнее, тесты зелёные.
5. Новая панель.
6. JOIN-пикер и бинд.

Шаги 1 и 4 — чистый рефакторинг, коммитятся отдельно от фич.
